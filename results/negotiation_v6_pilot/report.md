# 第六轮真实协商可行性试运行

3个真实MiniMax案例、10次已记录调用、8203 token。无人工故障注入，无脚本替代，无失败重跑。供应商/物流商模型提出资源选项，买方模型选择计划，各组织程序检查自身承诺，执行端要求同一计划的三方证据。

|案例|结果|模型调用|承诺查询|最终运费|观察|
|---|---|---:|---:|---:|---|
|优先省运费|完成|4|5|2400|初稿把bulk费用写成0；carrier否认后，模型修正为900。供应承诺复用|
|型号未批准|买方拒绝|3|0|—|模型依据本组织审批状态拒绝，无计划提交|
|优先复产|完成|3|3|2400|可行，但不是私有资源全集下最便宜的早到方案|

**首次出现真实的局部错误—程序拒绝—模型修正—继续完成轨迹。** 错误来自真实模型回答，没有注入。程序没有把第一份计划当成可执行承诺，carrier签署了transport_quote_mismatch否认，随后买方修正。修正只改变费用，供应商依赖未变，因此第二轮只重新请求carrier和buyer，累计5次而非全部重取的6次。

这条轨迹证明机制实际参与恢复，但没有同期随机对照，不能据此报告总体因果效应、稳定收益或“节省1/6费用”的总体估计。全计划绑定协议与依赖范围绑定协议的公平比较仍待执行；两者均须复用各自仍有效的缓存。

**业务质量仍存在明显问题。** 省运费案例中，模型把早到偏好理解为必须满足，最后选择2400方案；其已见bulk报价允许整批900方案。复产案例中，模型也选择2400；完整私有状态中存在2100的早到方案，但carrier没有披露road选项，不能把这部分差距全部归因于买方推理。

后验约束检查确认两份最终计划均可行，执行收据的三方签名和提交时有效期通过核验；可行性不等于偏好最优。候选方案比较使用本合成案例两批不可再分的离线枚举，读取私有状态仅发生在事后评估，不参与在线决策，也不是一般物流最优解证明。见diagnostics.json。

**局限与下一步：** 尚无跨物理设备部署，events.json目前是便于调试的轨迹，虽有组织签名消息和最终承诺，尚未具备v5完整审计封存及独立计数重建；下一批前需补齐。资源确认是合成静态状态，不是实际运输预留。接下来冻结协议，比较同样业务输入下的Autonomous、全计划证据和依赖范围证据，并分开自然错误与预注册故障注入。同时记录信息遗漏和偏好质量，避免把“能执行”误写成“业务做好了”。
