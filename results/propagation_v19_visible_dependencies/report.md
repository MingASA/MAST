# 依赖关系可见的真实对照

两组模型看到相同的claim_id、issuer、parents、rule及fact，明确允许检查依赖完整性。

|条件|提交时验证|接收前验证|
|---|---|---|
|正常|两跳均forward，最终可提交|两跳均forward，最终可提交|
|金额改错|首个模型hold，未转发|模型接收前阻断|
|遗漏依赖|模型调用RuntimeError，行为未知|模型接收前阻断|

5个成功模型决定的签名与实际请求摘要匹配；本批未再出现请求列表别名问题。记录5次成功调用、4802token，另一个调用失败用量未知。错误阶段为model_call，但RuntimeError具体原因没有记录，不能进一步断言是网络、截断或JSON问题。记录中的model_exposure_hops只计返回draft的跳数，失败调用不能解释为从未向模型发送输入。

没有观察到新的错误再转发，因此不声称比模型自主检查增加了最终安全性。接收前门禁确实在模型调用前拒绝了已知格式的无效派生声明；这里只支持确定性边界保障，不支持总体错误率优越性。

额外观察：正常记录中有模型reason把cents=10700解释为10700元。签名结构化fact仍为10700分，转发仅使用fact，不把reason作为权威事实。若产品直接转发解释文字，则当前机制不能保护这些文字的准确性。该错误说明需要明确“可执行/可引用声明”与非权威说明的边界，而不是宣称所有Agent输出都已验证。
